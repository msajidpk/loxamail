# Database Foundation V1

The LoxaMail application uses Prisma ORM 7.10 with MariaDB. Local development uses the separate database `loxamail_v1_dev`; the discarded `loxamail_dev` database is not part of this foundation.

Copy `.env.example` to `.env` and set `DATABASE_URL` to the local MariaDB credentials and `loxamail_v1_dev` database. Keep `.env` out of version control. Prisma CLI configuration is in `prisma7.config.ts`, and the schema is in `prisma/schema.prisma`.

Every persisted model has a UUID v4 primary key generated by Prisma using `String @id @default(uuid()) @db.VarChar(36)`. All relational UUID foreign keys use `String` with `@db.VarChar(36)`. Generated Prisma Client output is written to `generated/prisma/`, which is ignored by Git.

The initial migration is `prisma/migrations/20260930052020_init/`. It includes MariaDB CHECK constraints for the exactly-one-target rules on ActivityContext, TicketContext, DocumentRelation, and NotificationContext; the exactly-one-author rule on TicketMessage; and the AuditEvent actor context. Those checks are kept in migration SQL because Prisma Schema Language does not represent them.

AuditEvent stores its target kind as a bounded string and its target UUID as a historical weak reference, with no target foreign key. The approved closed target set and target existence must be validated by the future audit write path; this foundation does not freeze the still-undecided vocabulary as a database enum.

Statuses remain strings where the approved architecture lists candidate vocabularies rather than final enums. Product tax configuration remains an opaque optional reference; no Tax model or tax rules are introduced. Currency/rounding policy is not implemented; Prisma's default MariaDB Decimal mapping is used for decimal-valued fields without choosing application rounding behavior.

Foreign keys enforce reference existence. The approved same-CustomerAccount consistency rules across multiple linked records require transactional validation on create, update, and reassignment in future application write paths; this database foundation does not add application logic. Financial amount, currency, allocation, and adjustment invariants that span multiple records also remain transactional validations as defined by the architecture.

`RolePermission` is not persisted because database-managed Permission keys remain conditional. Product fulfillment stays generic on Product plus replaceable SupplierAssignment; there is no provider-specific model or ProductFulfillmentProfile table.
